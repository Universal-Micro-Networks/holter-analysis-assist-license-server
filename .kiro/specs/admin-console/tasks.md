# Implementation Plan

- [x] 1. 基盤: 画面の実行前提、データ追加、設定
- [x] 1.1 テンプレートと静的ファイルが Workers で配信できることの確認
  - 画面用テンプレートのファイルを Worker のバンドルに同梱する設定と、CSS・JavaScript を静的ファイルとして配信する設定を追加する
  - docker compose の開発サーバーで、テンプレートから描画した確認用ページと静的ファイルが取得できることを確認し、確認後に確認用ページを取り除く
  - 同梱できない場合は、テンプレートをコードに埋め込む方式に切り替え、その結論を設計と調査記録に反映する
  - 開発サーバーで、テンプレート由来の HTML と CSS・JavaScript がホストから取得できる
  - _Requirements: 1.2, 3.2_

- [x] 1.2 ライセンスへのメモと公開 ID の追加、操作記録テーブルの作成
  - メモ（200 文字以内、既定は空）と公開 ID（一意、推測困難）をライセンスに追加し、既存ライセンスにも公開 ID を付与するマイグレーションを作る
  - 追記専用の操作記録テーブル（フォーム単位の一意な要求 ID、運営者、操作の種類、対象ライセンス、変更前後の値、送信元、日時）を作る
  - API から発行したライセンスにも公開 ID が自動で付き、管理 API・クライアント API の応答の形は変わらない
  - ライセンスの読み取りでメモと公開 ID が得られるようにし、既存のテストをすべて通す
  - ローカル D1 とテスト用 SQLite の両方でマイグレーションが適用でき、既存の全テストが通る
  - _Requirements: 2.1, 4.1, 6.1, 6.3, 7.1, 8.6_

- [x] 1.3 管理画面の設定項目と日本時間の表示・期間変換
  - Access のチームドメインと対象アプリケーション識別子、画面セッションの秘密鍵、ローカル開発用の運営者を Workers の環境から読み取る
  - ローカル開発用の運営者の設定が本番用の設定ファイルに含まれないことを設定テストで保証し、雛形ファイルに開発用の値を追加する
  - UTC の時刻を日本時間の表示に変換し、日本時間の日付範囲（両端を含む）を UTC の半開区間に変換する
  - 設定の読み取りと時刻変換の単体テストが通る
  - _Requirements: 1.1, 5.5, 5.6_

- [x] 2. 中核: 認証・セッション・データアクセス・画面用サービス
- [x] 2.1 (P) 画面用リポジトリのテスト用実装と契約テスト
  - メモ・キーの部分一致（日本語、英字の大文字小文字を区別しない）、状態での絞り込み、並べ替え（既定は新しい順。上限・当月利用回数・発行日時の昇順・降順）、一致件数の取得を持つ一覧検索を作る。LIKE・GLOB は使わない
  - 公開 ID でのライセンス取得、要求 ID からの操作結果の取得、ライセンスごとの操作記録の取得を作る
  - 発行・上限変更・状態変更・メモ変更を、変更前後の値を持つ操作記録と同時に原子的に書き込む。要求 ID が重複した場合は何も変更せず二重送信として通知する
  - 契約テストで、検索結果と並び順、二重送信時にライセンスが変わらないこと、変更前後の値が記録されることが確認できる
  - _Boundary: ConsoleRepository_
  - _Requirements: 2.1, 2.2, 2.3, 2.4, 2.6, 2.7, 6.1, 6.3, 8.5_

- [x] 2.2 画面用リポジトリの D1 実装
  - 2.1 と同じ SQL を D1 の一括実行で動かし、二重送信・キー重複・その他の障害をそれぞれの例外に変換する
  - 偽の D1 を使った単体テストで、一括実行の内容と例外の変換を確認する
  - 開発サーバーのローカル D1 で、要求 ID の重複時に一括実行全体が取り消されること、変更前後の値の記録、日本語メモの部分一致検索が動くことを確認する
  - _Requirements: 2.2, 6.1, 8.5_

- [x] 2.3 (P) Access JWT の検証
  - RS256 の署名を、符号化の全体一致比較で検証する。署名方式の差し替え（`none`・共通鍵方式）は拒否する
  - 発行元・対象アプリケーション・有効期限・利用開始時刻・トークン種別・メールアドレスと利用者 ID の有無を検証する
  - 公開鍵を取得して 1 時間キャッシュし、未知の鍵 ID では 1 回だけ再取得する。取得失敗は一時的障害として扱う
  - テスト用の固定 RSA 鍵ペアで生成したトークンについて、正しいトークンの受理と、改ざん・期限切れ・対象不一致・方式差し替えの拒否が単体テストで確認できる
  - _Boundary: AccessVerifier_
  - _Requirements: 1.1, 1.2_

- [x] 2.4 (P) 運営者セッション
  - 運営者ごとの署名付き Cookie セッションを作り、新しいセッションの開始時にサインインを記録できるようにする
  - 最終操作から 8 時間を超えたセッションを失効させ、運営者が替わった場合はセッションと CSRF トークンを作り直す
  - 成功メッセージの受け渡しと、一覧の検索条件の保持を行う。ライセンスキーを検索条件以外で保存しない
  - サインアウトでセッションを消去する
  - 8 時間ちょうどは有効で超過すると失効すること、運営者の交代でトークンが変わることが単体テストで確認できる
  - _Boundary: ConsoleSession_
  - _Requirements: 1.4, 1.5, 6.4, 8.1_

- [x] 2.5 (P) 画面のセキュリティ部品
  - 変更操作の CSRF トークンを定数時間で比較し、送信元（Origin、なければ Referer）が自サイトであることを確認する
  - すべての画面応答に、他サイトへの埋め込み禁止、外部・インラインのスクリプト禁止、キャッシュ禁止、参照元を送らない、HTTPS のみを指示するヘッダーを付ける
  - トークン不一致・欠落・送信元不一致の拒否と、ヘッダーの付与が単体テストで確認できる
  - _Boundary: ConsoleSecurity_
  - _Requirements: 7.2, 7.3, 7.5, 7.6_

- [x] 2.6 (P) フォームの解析と日本語メッセージ
  - 発行・上限変更・メモ変更・検索・月選択・履歴期間の入力を解析し、項目ごとの誤りを返す（期間未指定は当月、開始が終了より後・形式不正は誤り）
  - エラー種別と入力誤りを、画面に表示する日本語の固定文言に変換する（見つからない、一時的障害で操作未完了、要求制限、二重送信、サインインが必要）
  - 境界値（上限 0 と 1,000,000、メモ 200 文字、改行・制御文字）を含む単体テストが通る
  - _Boundary: forms, messages_
  - _Requirements: 3.3, 3.4, 4.7, 5.4, 5.6, 8.2, 8.3, 8.4_

- [x] 2.7 画面用サービス
  - 一覧（1 ページ 20 件、全件数とページ数付き、当月利用回数付き）、詳細（選択月の利用状況と最新の操作記録）、発行（キー重複時の再生成）、上限変更、停止、再開、メモ変更、利用履歴（1 ページ 100 件）を提供する
  - 月間上限の検証は既存の規則を使い、メモの検証を追加する。状態が変わらない停止・再開は記録を残さない
  - 利用状況と履歴は既存の利用サービスを使い、暦月の規則を重複実装しない
  - テスト用リポジトリと固定時計による単体テストで、各操作の結果、操作記録、存在しない公開 ID の扱い、二重送信の通知が確認できる
  - _Depends: 2.1_
  - _Requirements: 2.1, 2.2, 2.3, 2.4, 2.6, 2.7, 3.1, 3.4, 4.1, 4.2, 4.3, 4.4, 4.5, 4.7, 5.1, 5.2, 6.1, 6.2_

- [x] 3. 画面の実装
- [x] 3.1 画面の共通部分（認証ガード、レイアウト、エラー表示、サインアウト）
  - 画面の経路すべてで、レート制限 → 運営者の識別 → セッション確認の順にガードを適用する。Access のトークンがない・不正な場合は内容を表示せず、運営者の存在を示さない固定文言の 403 を返す
  - ローカル開発用の運営者は、Access 未設定かつループバックのホストでのみ有効にする。どちらの手段もない場合や秘密鍵がない場合は 503 を返す
  - 無操作で失効したセッションは消去して Access のログアウトへ送り、サインアウト操作も同様にする
  - 共通レイアウトにサインイン中の運営者と成功メッセージを表示する。画面配下のエラーは HTML で返し、`/v1` 配下は従来どおり JSON のまま維持する
  - テストクライアントで、未サインインで内容が返らないこと、サインイン後に運営者が表示されること、失効とサインアウトの遷移、`/v1` の応答が変わらないことが確認できる
  - _Depends: 1.1, 1.3, 2.3, 2.4, 2.5, 2.6_
  - _Requirements: 1.1, 1.2, 1.3, 1.4, 1.5, 1.6, 6.4, 8.3, 8.4, 8.6_

- [x] 3.2 ライセンス一覧と検索の画面
  - 一覧にメモ・状態・当月利用回数・発行日時を新しい順に表示し、20 件ごとの番号付きページャーで移動できるようにする
  - 当月利用回数・発行日時の見出しで並べ替えられるようにし、並び順をページ移動と再検索で引き継ぐ（月間上限は画面に表示しない）
  - 検索ボタンは置かず、入力欄での Enter と状態の選択で検索する
  - 検索条件（メモ・キーの一部、状態）は POST で受け取ってセッションに保存し、一覧の URL にはページ番号と並び順だけを載せる
  - 該当がない場合はその旨を表示する
  - テストクライアントで、検索・絞り込み・並べ替え・ページ移動が動き、どの URL にもライセンスキーが含まれないことが確認できる
  - _Requirements: 2.1, 2.2, 2.3, 2.4, 2.5, 2.6, 2.7, 7.1_

- [x] 3.3 ライセンス発行の画面
  - 月間上限とメモの入力フォームを表示し、誤りは入力値を残したまま項目ごとに表示する
  - 発行後は詳細画面へ移動し、発行したキーと成功メッセージを表示する。キーをクリップボードへコピーする操作を用意する
  - 同じフォームの二重送信では 2 件目を発行せず、1 件目の詳細へ移動する
  - テストクライアントで、発行・入力誤りの再表示・二重送信で 1 件だけ発行されることが確認できる
  - _Requirements: 3.1, 3.2, 3.3, 3.4, 3.5, 8.1, 8.5_

- [x] 3.4 ライセンス詳細と変更操作の画面
  - キー、メモ、状態、月間上限、選択月の利用回数と残り回数、発行日時、最終更新日時、最新の操作記録を表示する
  - 上限変更、停止、再開、メモ変更を POST で行い、停止・再開と当月利用回数未満への上限変更では確認画面を挟む。成功後は詳細画面へ戻して成功メッセージを表示する
  - CSRF・送信元の検証に失敗した操作と、存在しないライセンスへの操作は実行せずに表示する。削除の操作は設けない
  - テストクライアントで、各変更と確認画面、操作記録の表示、CSRF トークンなしの拒否でデータが変わらないことが確認できる
  - _Requirements: 4.1, 4.2, 4.3, 4.4, 4.5, 4.6, 4.7, 4.8, 5.1, 6.1, 6.2, 6.3, 7.3, 8.1, 8.2, 8.5_

- [x] 3.5 利用履歴の画面
  - 日本時間の日付で期間を指定し（未指定は当月）、利用日時を古い順に日本時間で表示し、続きを順に表示できるようにする
  - 期間の誤りは履歴を表示せずに入力誤りを表示する
  - テストクライアントで、期間指定・未指定・続きの表示・入力誤りが確認できる
  - _Requirements: 5.2, 5.3, 5.4, 5.5, 5.6_

- [x] 4. 統合: 本番用の依存関係の結線
  - 本番の依存生成を画面と API の双方を知る組み立て層へ移し、Workers の環境から D1・サービス・Access 検証器（公開鍵はランタイムの fetch で取得）・セッション設定を生成する
  - 画面のアクセスログに運営者を加え、URL の公開 ID やキー、トークン、Cookie の値が出ないようにする
  - docker compose の開発サーバーで、ローカル開発用運営者として画面から発行 → 上限変更 → 停止 → 再開 → メモ変更 → 操作記録の確認までを行うスクリプトが成功し、ランタイムの fetch で外部の公開鍵を取得できることを確認する
  - _Depends: 2.2, 3.1, 3.2, 3.3, 3.4, 3.5_
  - _Requirements: 1.1, 6.1, 6.4, 7.4, 8.6_

- [x] 5. 検証
- [x] 5.1 画面の結合テスト
  - 偽の Access 鍵で署名したトークンを使い、サインインから発行・変更・停止・再開・メモ変更・利用履歴・サインアウトまでの一連の操作を通す
  - すべての画面応答にセキュリティヘッダーが付き、画面の URL と HTML 内のリンクにライセンスキーが含まれず、入力したメモがエスケープされて表示されることを確認する
  - データ保存の障害を模擬したとき、内部情報を含まない一時的障害が表示され、データが変わらないことを確認する
  - `uv run pytest`（および `docker compose run --rm test`）で既存を含む全テストが通る
  - _Requirements: 1.1, 1.2, 1.4, 3.1, 4.2, 4.3, 4.4, 4.5, 5.2, 6.1, 6.2, 7.1, 7.5, 7.6, 8.3, 8.6_

  - 既存の通し確認と同時要求の検証スクリプトも再実行し、結果が変わらないことを確認する
  - 検証スクリプトを実行し、上記の結果が再現できる
