  - Workers の設定に、Python Workers の互換フラグ、D1 バインディング、レート制限バインディング（60 秒あたり 120 回）、Workers Logs の有効化を定義する

  - `uv sync` が成功し、`uv run pytest` がテスト 0 件で正常終了する
  - _Requirements: 7.3_

- [x] 1.2 ドメインの型・エラー種別・リポジトリ契約の定義
  - ライセンス、ライセンス状態、集計期間、利用状況サマリ、利用履歴エントリのデータ型を定義する

  - ライセンスと利用履歴それぞれのリポジトリ契約（取得・作成・上限変更・状態変更・上限判定付き挿入・期間内件数・期間内一覧）と、永続化障害を表す例外を定義する
  - 型チェック可能な形で import でき、エラー種別が互いに区別できることを単体テストで確認できる
  - _Requirements: 8.2_

- [x] 1.3 データベーススキーマのマイグレーション作成
  - ライセンス表（キー、月間上限、状態、作成・更新日時）と利用履歴表（自動採番 ID、ライセンスキー、利用日時）を作成する
  - 月間上限は 0 以上、状態は有効・停止のみを許す制約を付け、利用履歴はライセンスへの参照を持ち削除を制限する
  - ライセンスキーと利用日時の複合インデックスを作成する
  - 利用履歴に推論の入力データや結果を保存する列を持たせない
  - ローカル D1 へのマイグレーション適用でテーブルとインデックスが作成され、Python 標準の SQLite にも同じ SQL を適用できる
  - _Requirements: 2.6, 3.1, 5.6_

- [x] 1.4 Flask アプリの骨格・共通応答形式・Workers エントリポイントの作成
  - アプリ生成処理を作り、Workers のエントリポイントから WSGI 経由で公開する
  - 成功・失敗の共通応答形式と、エラー種別から HTTP ステータスへの対応を実装する
  - サービス例外は対応するエラー応答に、永続化障害と想定外の例外は内部情報を含まない一時的障害（503）に変換する。未定義のパスや許可されていないメソッドも同じ形式で返す
  - 認証・レート制限・DB アクセスを伴わないヘルスチェック用エンドポイントを追加する
  - Flask の同期ハンドラから `run_sync` で D1 に簡単な問い合わせができること、パッケージ配下のモジュールを import できることを `uv run pywrangler dev` で確認する（確認用の処理は確認後に削除する）
  - ヘルスチェックが 200 と共通形式の応答を返し、存在しないパスが共通形式のエラーを返す
  - _Requirements: 8.1, 8.2, 8.3_

- [x] 1.5 Docker / docker-compose によるローカル環境の構築
  - Node.js・uv・Python を含む開発用イメージを作り、ビルド時に Python 依存と wrangler をインストールする。amd64 と arm64 の両方でビルドできるようにする
  - 開発サーバー用サービスは、起動時に依存の同期、ローカル D1 への未適用マイグレーションの適用、全インターフェースでの開発サーバー起動を順に行う
  - ソースコードをバインドマウントし、ローカル D1 のデータ・pywrangler の生成物・node_modules・uv キャッシュは名前付きボリュームに置いてホストに書き出さない
  - テスト用サービスは通常の起動では立ち上がらず、個別実行でテストを走らせる。ヘルスチェックエンドポイントを使った healthcheck を設定する
  - `docker compose up` 後にホストの `localhost:8787` でヘルスチェックが 200 を返し、`docker compose run --rm test` でテストが実行される

- [x] 2. ドメイン規則の実装
- [x] 2.1 (P) 集計期間と時刻表現の実装
  - サーバーの現在時刻（UTC）から、日本時間の暦月に基づく半開区間（月初を含み翌月初を含まない）を求める
  - 年・月の指定から同じ形式の期間を求める
  - 時刻を UTC のミリ秒付き固定長文字列に変換し、文字列の大小と時刻の前後が一致するようにする
  - 日本時間の月末最終時刻と月初、UTC では前日にあたる時刻、12 月から 1 月への年またぎの単体テストがすべて通る
  - _Boundary: domain_
  - _Requirements: 2.3, 3.1, 3.4_

- [x] 2.2 (P) ライセンスキーの生成・検証・フィンガープリントの実装
  - 128 ビットの暗号学的乱数から、接頭辞付きの固定形式のライセンスキーを生成する
  - 文字列がライセンスキーの形式に一致するかを判定する
  - ログ出力用に、キーを復元できない短いフィンガープリントを求める
  - 生成したキーが常に形式に一致し、形式外の値（空、長さ違い、大文字、別接頭辞）を拒否する単体テストが通る
  - _Boundary: domain_
  - _Requirements: 1.4, 5.1, 7.4_

- [x] 3. 永続化層の実装
- [x] 3.1 (P) テスト用 SQLite リポジトリの実装と契約テスト
  - Python 標準の SQLite にマイグレーションを適用し、リポジトリ契約を満たすテスト用実装を作る
  - 上限判定付き挿入は、ライセンスが有効かつ当月件数が上限未満のときだけ 1 件挿入する単一の SQL 文で行い、挿入後の当月件数を返す
  - 期間内一覧は ID 順で、指定 ID より後から指定件数を返す
  - 上限ちょうどで挿入が拒否されること、停止中・未登録では挿入されないこと、前月の履歴が当月件数に含まれないこと、上限変更が直後の判定に反映されることを契約テストで確認できる
  - _Boundary: repository fake_
  - _Requirements: 2.1, 2.4, 3.1, 3.2, 3.4, 3.5, 5.6_

- [x] 3.2 (P) D1 リポジトリの実装

  - 上限判定付き挿入と挿入後の当月件数取得を 1 回のバッチ（トランザクション）で実行し、挿入件数で許可・拒否を判定する
  - D1 の例外はすべて永続化障害に変換し、詳細はログにのみ出力する。削除操作は提供しない
  - `uv run pywrangler dev` 上で、ライセンスの作成・取得・上限判定付き挿入・件数取得が期待どおりの結果を返す

- [x] 4. サービス層の実装
- [x] 4.1 (P) ライセンスサービスの実装
  - クライアント処理の共通前提として、未登録ならライセンス無効、停止中なら利用停止中のエラーを出す有効性判定を実装する
  - 月間上限を指定した発行を実装し、キーが重複した場合は再生成して最大 3 回まで再試行する
  - 上限変更・停止・再開を実装し、対象がなければライセンス未登録（管理用）のエラーを返す。停止中への停止と有効への再開は冪等に成功させる
  - 月間上限は 0 以上 1,000,000 以下の整数のみ受け付け、真偽値・小数・負数を拒否する
  - テスト用リポジトリを使った単体テストで、上記の成功・失敗と、停止しても利用履歴が残ることを確認できる
  - _Boundary: LicenseService_
  - _Depends: 2.2, 3.1_
  - _Requirements: 1.1, 1.2, 1.3, 5.1, 5.2, 5.3, 5.4, 5.5, 5.6_

- [x] 4.2 (P) 利用サービスの実装
  - 注入した時計から利用日時と当月期間を決め、上限判定付き挿入を 1 回だけ呼んで利用を記録する。挿入されなければ理由（未登録・停止中・上限到達）を判定してエラーを出す
  - 記録成功時に、記録後の当月利用回数・月間上限・残り回数・集計期間を返す
  - 当月状況の照会は読み取りのみで行い、未登録・停止中ならエラーを出す
  - 管理用として、指定月の利用回数と、期間指定・ページ送り付きの利用履歴一覧を、ライセンスの状態に関わらず返す（一覧の件数は 1〜1000、既定 100）
  - テスト用リポジトリと固定時計を使った単体テストで、上限 N に対し N 回成功・N+1 回目が上限到達になること、照会で履歴が増えないこと、月が変わると回数が戻ることを確認できる
  - _Boundary: UsageService_
  - _Depends: 2.1, 3.1_
  - _Requirements: 2.1, 2.2, 2.3, 2.4, 3.1, 3.2, 3.4, 3.5, 4.1, 4.2, 4.3, 6.1, 6.2_

- [x] 5. HTTP 層の実装
- [x] 5.1 (P) 認証とレート制限ガードの実装
  - Authorization ヘッダーの Bearer 形式からライセンスキーを取り出し、欠落や形式不正を要求不正とする
  - 管理トークンを定数時間で比較し、不一致や未設定の場合は認証エラーとする（未設定時は常に拒否）
  - 送信元 IP をキーにレート制限バインディングを呼び、超過時はレート制限エラーとする。バインディングが未設定・エラーの場合は制限せずに続行する
  - ログにはライセンスキーの代わりにフィンガープリントを出し、Authorization ヘッダーは出力しない
  - 単体テストで、キーの抽出・形式不正・管理トークン一致／不一致／未設定・レート制限の許可／超過／バインディング異常時の続行を確認できる
  - _Boundary: auth, rate_limit_
  - _Depends: 2.2_
  - _Requirements: 1.4, 7.1, 7.3, 7.4_

- [x] 5.2 クライアント向け API の実装
  - 有効性確認、利用記録、当月状況照会の 3 つのエンドポイントを、設計の契約どおりのメソッド・応答で実装する
  - 各エンドポイントの最初にレート制限を適用し、ライセンスキーは Authorization ヘッダーからのみ受け取る（URL には含めない）
  - 利用記録はリクエストボディを必要とせず、送られても保存しない。履歴を変更・削除するエンドポイントは提供しない
  - 未登録キーへの応答は固定文言とし、他のライセンスの存在や内容を含めない
  - Flask テストクライアントとテスト用リポジトリで、3 つのエンドポイントが成功時に設計どおりの応答を返し、未登録・停止中・上限到達・形式不正で対応するエラー種別を返す
  - _Depends: 4.1, 4.2_
  - _Requirements: 1.1, 1.2, 1.3, 1.4, 1.5, 2.1, 2.2, 2.4, 2.6, 3.2, 4.1, 4.2, 4.3, 6.3_

- [x] 5.3 (P) 管理 API の実装
  - ライセンスの発行・取得・上限変更・停止・再開と、利用履歴一覧・月別利用回数の各エンドポイントを、設計の契約どおりすべて POST で実装する
  - 対象ライセンスキーは JSON ボディで受け取り、URL には含めない。期間は タイムゾーン付き ISO 8601 を UTC に正規化して半開区間として扱い、月は年-月形式で受け取る
  - すべてのエンドポイントで管理トークンによる認証とレート制限を適用し、入力値（上限値・期間・月・件数）を検証する
  - Flask テストクライアントで、管理トークンなしでは認証エラー、正しいトークンでは各操作が成功し、存在しないキーではライセンス未登録（管理用）を返す
  - _Boundary: admin_routes_
  - _Depends: 4.1, 4.2, 5.1_
  - _Requirements: 5.1, 5.2, 5.3, 5.4, 5.5, 6.1, 6.2, 7.1_
